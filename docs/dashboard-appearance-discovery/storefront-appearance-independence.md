# Storefront independence

The existing dashboard appearance page calls `syncBrandColorsToActiveTheme` after saving user colors. It reads the active website theme through `src/lib/api/themeApi.ts` and updates that theme. This is an existing coupling, not a new tenant workspace implementation. Restaurant theme storage and public theme retrieval serve independently branded storefront output. The future change must explicitly decide how existing personal customizations and active storefront themes are retained, remove implicit coupling only with tests and a migration policy, and verify saving or resetting workspace appearance leaves the storefront unchanged. No storefront configuration has been altered in this discovery.

The storefront's `components/providers/theme-provider.tsx` reads `lib/store/theme-store.ts`, selects dark or light color fields using `next-themes`, writes `--theme-*` properties and calls `applyTypographyVariables`. `lib/api/get-theme-server.ts` loads the theme server-side by restaurant slug and documents caching; inspect exact invalidation and response scope before modifying. These variables and tenant storefront settings are distinct from dashboard `--primary-*` shades.

In `frontend/apps/dashboard/src/app/[locale]/dashboard/settings/appearance/page.tsx:137`, a successful user-color PUT updates the personal preferences store, then attempts the website-theme update. A thrown sync error is logged as a warning, after which the UI still sets the save status to success. Thus a successful personal save does not establish that storefront synchronization succeeded. The sync reconstructs a configuration containing existing typography, identity, header, footer, components and custom CSS along with the merged colors; preserve those fields and test partial-failure behavior before any decoupling. This is a source-level observation, not a claim that a live customer theme was modified in this discovery.
