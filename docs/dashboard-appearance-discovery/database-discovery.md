# Database discovery

`backend/migrations/040_create_user_settings.sql` creates user-owned settings with theme and three color values; defaults are blue, indigo and green. `backend/migrations/165_rls_user_settings.sql` enables and forces RLS for user settings and related audit/security tables using the owner user's tenant. `backend/internal/repository/user_settings_repo.go` performs tenant-scoped transactions through `backend/internal/pkg/database/tenant_tx.go`; it validates hexadecimal colors and stores user-level changes. Existing `themes`, restaurant theme/configuration and website settings migrations under `backend/migrations/063_*` through `090_*`, plus `161_*`–`163_*`, require detailed schema and active-path review before reuse. Those records must not be assumed to represent internal workspace appearance.

Migration `067_create_themes_table.sql` associates `themes` with restaurant and tenant; `070_create_themes_v2_table.sql` also carries both identifiers, and `077_enhance_themes_with_jsonb_config.sql` adds JSONB configuration. Those fields alone do not establish workspace ownership or effective isolation. The user-settings handler checks path user ID against authenticated claims. Its current update and `LogAuditChange` calls occur separately; a future tenant appearance write should explicitly test atomic update plus audit instead of assuming the existing sequence provides atomicity.

The original `themes` definition is one row per restaurant and includes site template, five color columns, `font_family`, base size, radius, logo and favicon. The initial `themes_v2` definition permits multiple restaurant/slug records and adds active/published status, seven color columns, typography, line height and website identity. Migration 077 adds a GIN-indexed JSONB `config` that can hold colors, typography, header, footer and homepage settings. These are website-oriented schemas; neither column names nor a JSONB document imply that records are valid tenant-workspace settings. Inspect later constraints, RLS and the actual v2 service/repository before migration or reuse.

In migration 040, `user_settings.user_id` is unique and references `users(id)` with cascade deletion; the row has no direct `tenant_id`. `theme` accepts `light`, `dark`, or `system`; `language` accepts `en` or `ar`; `primary_color`, `secondary_color`, and `accent_color` are seven-character `#RRGGBB` strings with database checks. It also stores notification preferences and timestamps. `user_settings_audit_log` records subject user, setting name, old/new text, actor, timestamp and IP. Password history and email-change tables are security records, not appearance configuration.

Migration 165 enables and forces RLS on these four tables for `pos_app`. Its `user_settings` policy resolves the row owner through `users.tenant_id` and the transaction-local `app.tenant_id`; the audit policy checks both subject and actor tenant. This is a source-level description, not a new runtime isolation test. `user_settings_audit_log.changed_by` is declared NOT NULL while its foreign key specifies `ON DELETE SET NULL` in the original migration; verify later migrations and deletion behavior before designing audit retention around it.

No tenant-workspace appearance table, migration, data migration, RLS policy or tenant-isolation test was created here. Complete the migration ordering, grant, rollback, auditing and cross-tenant behavior review before implementation.
