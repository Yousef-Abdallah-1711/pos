# Permissions and tenant isolation

The dashboard sidebar filters entries using `src/hooks/useRbac.ts` and `src/lib/rbac.ts`; this is a presentation control, not proof of API authorization. Server routes use `wrapProtected` or module-specific `wrapWithPermission` in `backend/cmd/api/main.go`. Tenant context is obtained by middleware and repositories can use `database.WithTenantTx` to set transaction-local RLS context. The existing user-settings policies derive tenant ownership through `users`.

Future writes must have a specifically chosen tenant-admin permission, server-side tenant context, forced RLS, actor-aware audit, bounded input, and concurrency protection. Verify user, tenant and restaurant scope at each layer and write negative tests for cross-tenant access, no tenant context, invalid actor and missing permissions. Do not expose tenant IDs as authoritative client input. Actual current role assignments and complete route-level permission coverage remain unverified.

`backend/internal/pkg/database/tenant_tx.go` validates a positive tenant ID and nonnegative restaurant/user IDs, opens a transaction and sets `app.tenant_id`, `app.restaurant_id` and `app.user_id` via transaction-local `set_config(..., true)`. A zero restaurant denotes tenant-wide work; `WithTenantUserTx` requires a positive user ID. It rolls back on errors or panic and commits only after the callback succeeds. This design is intended to prevent a pooled connection carrying scope into the next transaction; verify the new repository actually uses it and that the deployed runtime role cannot bypass RLS.

The synthetic owner, seeded Manager/Employee and unassigned staff observations are documented in [sidebar evidence](sidebar-and-layout.md). In the one unassigned staff session, direct GETs to product and admin-theme APIs returned 403 even though a theme-builder shortcut was visible on the dashboard. These are useful spot checks, not a full privilege matrix. Test direct API requests, forged client tenant IDs, cross-tenant resource identifiers, role changes, no context, transaction rollback, stale revisions, cache invalidation and concurrent requests with a real disposable PostgreSQL instance. Test both read and write paths independently; successful hiding of a navigation item is never the authorization boundary.
