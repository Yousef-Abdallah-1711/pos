# SERVIO Authentication Implementation Roadmap

**Status:** Proposed phases for owner review; implementation has not started. No code, schema, infrastructure or deployment was changed during this audit.

## Decision summary

**VERIFIED CURRENT BEHAVIOR:** Go API already issues opaque host-only session cookies backed by Redis, has route-level Origin checks, atomic session rotation, tenant claim enforcement and a separate Super Admin session. Dashboard can restore a cookie session. **OBSERVED DEFECT:** Landing does not restore/display session; tenant-proof consumption and rate limits are process-local; several legacy browser bearer paths coexist; canonical domain and identity semantics need decisions.

**PROPOSED DESIGN:** Incrementally improve the current session system. Preserve narrow host-only API cookie. Add landing session island or BFF, shared atomic proof/rate-limit state, immediate revocation/version semantics and full E2E/scale evidence. Introduce OIDC only if federation/business requirements justify it.

**VERIFIED CURRENT BEHAVIOR:** Main staff auth uses a Redis-backed opaque cookie; Dashboard and Super Admin restore sessions; Landing does not. **OBSERVED DEFECT:** Cross-portal header state is incomplete, the single-use tenant proof and IP limits are process-local, and the staging domain/access policy is inconsistent. **UNVERIFIED ASSUMPTION:** Current source revision remains the intended implementation baseline when work begins. **REQUIRED BUSINESS DECISION:** Canonical origins, identity/membership model, session lifetime, privileged MFA, storefront accounts, production SLO and budget must be agreed before dependent phases.

Effort estimates are engineering person-days, not calendar commitments. They include code/review but exclude owner decision wait and unknown CI duration. Paths are starting points confirmed during audit; implementation must inspect current branch before edits.

## Essential before integrated session launch

P0: Phase 0 baseline, Phase 1 API contract, Phase 2 shared proof/revocation correctness, Phase 3 cross-portal session check, Phase 5 dashboard recovery, Phase 7 privileged boundary verification, Phase 10 security E2E, Phase 11 staged signed release. Phase 4 is the visible landing integration and must ship before claiming authenticated header UX. Phase 6 is required only if product wants tenant switching; current multi-tenant login selection can remain until the user/membership model is decided. Phase 8 is required to remove staff-token confusion but customer accounts are optional. Production readiness additionally requires Phase 9/12 performance/operational evidence.

## Blocking owner decisions

1. Canonical dashboard and production origins; whether legacy aliases redirect or retire.
2. Single global user with tenant memberships versus intentional tenant-scoped user rows.
3. Session idle/absolute lifetime, remember-me, current-device versus all-device logout.
4. Super Admin MFA/step-up and allowed network policy.
5. Customer storefront accounts versus anonymous/capability-based order access.
6. Production latency/error SLO, peak restaurant/order/KDS mix, geography and spend ceiling.
7. Screenshot/trace retention and redaction policy.

## Audit limitations and release guardrails

**UNVERIFIED ASSUMPTION:** Source branch changes after the recorded SHA may alter app behavior; rebase/re-audit before coding. The checked-out worktree also has pre-existing uncommitted KDS changes and SQL seed files; those were preserved. The live staging server is on the older receipt SHA, so source findings and live behavior must be rechecked against the exact candidate.

Do not begin a session redesign by widening cookie Domain, deleting legacy paths wholesale, changing schema without membership decision, or claiming 10k capacity from the current staging host. Do not deploy until required CI, signing, migration/backup/rollback, and auth acceptance gates are green.
