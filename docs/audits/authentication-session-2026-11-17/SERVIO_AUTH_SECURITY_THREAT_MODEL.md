# SERVIO Authentication Security Threat Model

**Audit date:** 2026-11-17 UTC · **Scope:** source inspection and read-only staging observations. No live exploit attempts were run.
Each item is labeled **VERIFIED CURRENT BEHAVIOR**, **OBSERVED DEFECT**, **PROPOSED DESIGN**, **UNVERIFIED ASSUMPTION**, or **REQUIRED BUSINESS DECISION**. Severity describes plausible impact if the relevant precondition exists; it is not a statement that an exploit was observed.

## System assets and trust boundaries

- Staff credentials, opaque session cookie, JWT signing secrets, Redis session keys, tenant/restaurant data, payment/business operations, Super Admin identity and impersonation controls.
- Browser UI origins are separate principals; API CORS uses exact configured origins and credentialed requests.
- API trust boundaries: browser → Caddy TLS edge → Go API; Go API → Redis/PostgreSQL over private compose networks.
- Tenant boundaries depend on signed claims, server-side membership, restaurant ownership verification, handler authorization and database filters/RLS.
- Customer storefront is public and uses order access/capability tokens; this is separate from staff authentication.

## Threat register

| Threat / severity | Preconditions and affected source | Current evidence and impact | Remediation and verification |
|---|---|---|---|
| **Tenant breakout / forged tenant context — High** | Authenticated request plus handler that trusts caller tenant/restaurant fields; `middleware/tenant.go`, route wrapping, individual repositories/handlers. | **VERIFIED CURRENT BEHAVIOR:** Tenant middleware takes tenant from JWT and ignores mismatched `X-Tenant-ID`; restaurant ID is verifier-checked when not fixed in claims. This is a strong control. However every protected route must be checked for correct middleware and resource-level authorization. **UNVERIFIED ASSUMPTION:** full route coverage was not exhaustively enumerated. | Build generated route→auth→tenant→permission matrix; ensure tenant-sensitive repository predicates and RLS are effective. Test A-user requests B tenant IDs/resources across read/write/export/WebSocket routes; expect deny and no data in response/log. |
| **Login proof replay across replicas — High** | Multi-tenant login proof obtained by a valid user; requests reach different API replicas. `auth_usecase.go:235-278`. | **VERIFIED CURRENT BEHAVIOR:** One-time proof consumption is process-local while API is designed to allow horizontal scaling. Another replica can lack the consumed marker and may accept replay until proof expiry. | Put proof `jti` in shared Redis with atomic consume + TTL, bind to email and allowed tenants, never log token. Test replay sequentially and in parallel across two app instances. |
| **Super Admin session compromise — Critical** | Admin credentials/session stolen, weak authentication or exposed admin origin. `super_admin_handler.go`, `super_admin_auth.go`, admin UI. | **VERIFIED CURRENT BEHAVIOR:** Dedicated cookie/token validator; active account, IP whitelist, rate-limit and `RequireSuperAdmin` middleware are present. **UNVERIFIED ASSUMPTION:** MFA, step-up for destructive actions and effective whitelist configuration are not proven. Current admin origin shares registrable domain and API session store infrastructure, though cookie name and validator differ. | Require MFA/step-up for sensitive actions; separate security policy and short absolute lifetime; confirm allowlist and trusted proxy values; consider distinct registrable domain. Test staff cookie cannot authorize admin endpoints and vice versa. |
| **Legacy bearer credential in browser storage — High** | XSS or compromised browser extension reads legacy token/localStorage; dashboard `lib/api.ts`, storefront `lib/api-client.ts`, localStorage compatibility paths. | **VERIFIED CURRENT BEHAVIOR:** Dashboard API helpers read persisted auth state and can attach Bearer; current auth provider removes old `token` and `auth-storage`, strips Authorization on its fetch wrapper. Storefront client reads `auth-token` from localStorage and may send it with requests. The route mix means risk varies by call path. | Inventory each actual endpoint and caller. Keep browser session opaque/HttpOnly, remove legacy persistence after compatibility proof. Scan browser storage under synthetic test. XSS prevention remains necessary even after token removal. |
| **Session hijacking / fixation — High** | Attacker steals cookie via endpoint compromise/XSS or can inject cookie via a sibling domain. | **VERIFIED CURRENT BEHAVIOR:** 32 random bytes opaque ID, host-only cookie, HttpOnly/Secure production, session ID hash as Redis key; login rotates a known valid session ID; refresh rotates ID atomically. **UNVERIFIED ASSUMPTION:** all TLS, Redis ACL and host-level compromise defenses in production. | Keep host-only scope, secure deployment, TLS, Redis ACL/network isolation, HSTS, secret rotation. Add session metadata and device revoke. Test cookie attributes on production HTTPS and session fixation cases. |
| **Cookie tossing / subdomain takeover — High if parent cookie used** | Broad `Domain=.rakmyat.online` cookie, or compromised/unclaimed sibling subdomain. | **VERIFIED CURRENT BEHAVIOR:** Current staff/admin cookie omits `Domain`, avoiding sibling delivery. Tenant host provisioning is manual and verified in runbook. | Do not widen Domain. Keep DNS/certificate/proxy tenant onboarding allowlisted; monitor dangling DNS; test malicious Domain cookie shadowing and reject ambiguity. |
| **CSRF — Medium/High** | Victim has valid cookie; attacker can induce state-changing browser request and Origin checks fail open or endpoint is unwrapped. | **VERIFIED CURRENT BEHAVIOR:** `SameSite=Lax`; unsafe session middleware checks configured Origin; auth login/confirm/refresh have trusted-Origin wrappers; logout checks Origin when session cookie exists; CORS exact allowlist. A double-submit CSRF helper exists but no registration call was found in `main.go`. Cookie-auth routes not using the shared middleware need route coverage audit. | Keep strict Origin validation, reject absent Origin for browser-cookie writes; use synchronizer/double-submit token only if it can be correctly delivered/read across origins (via BFF or API-readable CSRF cookie on API domain). Maintain route matrix and negative tests for all unsafe methods. |
| **XSS / account takeover — High** | Script execution in any app origin that can make credentialed API calls; `HttpOnly` prevents direct cookie read but not authenticated action. | **VERIFIED CURRENT BEHAVIOR:** Session cookie HttpOnly. No complete app-wide XSS/dependency review performed here. Landing client login and app script can issue authenticated cross-origin calls when CORS allows that origin. | Strong CSP/nonces, output encoding, dependency scanning, no unsafe DOM sinks; minimize session DTO and privilege; test CSP and stored/reflected XSS in isolated environment. |
| **Cross-origin credential leakage / CORS misconfiguration — High** | Wildcard or attacker-controlled origin combined with credentials; compromised allowed origin. `middleware/cors.go`, `CORS_ORIGINS`. | **VERIFIED CURRENT BEHAVIOR:** CORS compares configured normalized origins, returns exact origin and credentials true, varies by Origin. It supports one-level wildcard patterns if configured. Staging list is four exact origins. | Prohibit broad production wildcards for credentialed origins; validate config at startup; continuously test preflight from allowlisted and evil origins; treat each allowed UI host as trusted code. |
| **Open redirect — Medium/High** | User-controlled return/redirect URL passed through login flow or callback. | **VERIFIED CURRENT BEHAVIOR:** Current login callback uses configured dashboard URL; tested source points to fixed base and locale. Full scan of every redirect parameter and deep-link branch not exhaustive. | Use allowlisted canonical origins and relative paths; validate path prefix/encoding; reject scheme-relative, user-info, alternate ports and IDN confusables. Add malicious redirect acceptance cases. |
| **Refresh token replay / concurrent refresh race — Medium** | Old cookie reused after rotation or Redis atomic semantics fail. | **VERIFIED CURRENT BEHAVIOR:** No browser refresh token returned; opaque session cookie is rotated. Redis atomic rotation implementation and unit test expect one concurrent winner. | Preserve atomic consume, treat duplicate 401 as revalidation not retry storm; alert on replay; test on actual Redis adapter with multi-process concurrency. |
| **Stale roles/account disable after JWT issuance — High** | Role or active status changes while JWT/session remains valid up to TTL; API validates signed token but may not reread current role for every operation. | **VERIFIED CURRENT BEHAVIOR:** JWT claim role/tenant is validated; session key can be revoked. Super Admin additionally performs active account/session validation. Regular-user immediate global revocation/password invalidation was not established. | Add `authz_version`/membership version or server-side status check for privileged calls; revoke active sessions on password reset/disable; bounded cache with event invalidation. Test role-change propagation. |
| **Session replay after logout — Medium** | Client retains old JWT through legacy bearer path or API route bypasses session resolution; a cookie session is revoked but access token escaped elsewhere. | **VERIFIED CURRENT BEHAVIOR:** Cookie session path revokes Redis key; middleware still supports bearer JWT fallback. JWT could remain usable until expiry when sent directly to bearer-only endpoints, depending on route path. | Route audit and narrow legacy bearer exceptions; do not expose token to browser; test old bearer across each endpoint after logout and remove browser bearer once integrations migrate. |
| **Brute force / credential stuffing / enumeration — Medium/High** | Public login endpoint, distributed attacker or user enumeration through errors/timing. | **VERIFIED CURRENT BEHAVIOR:** IP-based in-process limits (20/min user login; 10/min registration; 10/min admin login); generic user login credential error. Multi-tenant names generic IDs; forgot-password behavior not verified. | Shared distributed rate limits by IP/account/device, backoff and anomaly alerts, CAPTCHA/step-up when risk threshold hit, timing and response parity. Test multi-replica bypass and email existence disclosure. |
| **Rate limiter exhaustion / spoofed client IP — Medium** | Many distinct IP keys or untrusted forwarded header chain. | **VERIFIED CURRENT BEHAVIOR:** code maintains process-local maps; Super Admin middleware extracts forwarded address only for trusted proxies. Allocation cleanup/fleet coordination are weak points for scale. | Bound/expire map if retained; prefer shared gateway/Redis limiter, set trusted proxy CIDRs explicitly and test spoofed XFF. |
| **Cross-tenant CDN cache leakage — Critical** | Personalized API/dashboard response enters shared cache keyed without user/tenant. | **VERIFIED CURRENT BEHAVIOR:** API global `NoStoreAPIResponses`; session response no-store; staging Dashboard sends private/no-store. Landing public HTML uses `s-maxage=300` and does not render user header, therefore current public caching avoids personalization. | Keep auth endpoints `no-store`, never vary public CDN by raw cookie, cache only public shell/assets; test two synthetic tenants against warm shared cache and inspect response headers/body. |
| **Unauthenticated staging UI exposure — Medium (environment-dependent)** | Public network access to a staging app before access review; staging contains operational or customer-like data. | **VERIFIED LIVE OBSERVATION:** Anonymous GETs to landing, dashboard and Super Admin login origins returned app responses without `WWW-Authenticate`. Active Caddy config is deployed `Caddyfile.public`, which has no Basic Auth. Staging responses include `X-Robots-Tag: noindex,nofollow`, but that is not access control. **OBSERVED DEFECT:** Runbook says root Caddyfile Basic Auth is current and public config activates only after accepted promotion. | Owner/security decision: keep staging public with synthetic-only data, or gate every UI host with SSO/VPN/Basic Auth at edge. Reconcile runbook with mounted config. Verify all five hosts, API exposure, logout/login and monitoring after policy change. |
| **Session/cache unavailability — High availability** | Redis outage or eviction; API session lookup fails. | **VERIFIED CURRENT BEHAVIOR:** Production requires Redis; session auth fails closed. Staging Redis uses `maxmemory 48mb`, `noeviction`; no Redis HA topology verified. | Alert and capacity-plan Redis; explicitly define outage behavior (protected UI retry, no fallback to local store); test Redis loss and restoration without silently authenticating stale state. |
| **Customer order capability token leakage / IDOR — High** | Guessable order ID or tracking token leaked through URL/referrer/log; public order APIs. | **VERIFIED CURRENT BEHAVIOR:** Storefront maintains order token and sends `X-Order-Token`; endpoint-level behavior not fully reviewed here. | Use high entropy capability token, restrict status fields/actions, strip query tokens from referrer/logs, rate limit lookup and test cross-order denial. Do not merge customer identity with staff session without owner decision. |
| **Admin error disclosure — Low/Medium** | Failed privileged login or API errors exposed to attacker. | **VERIFIED CURRENT BEHAVIOR:** Super Admin login handler returns `err.Error()` and logs error details, unlike generic staff error response. | Return generic external error plus request ID; restricted redacted logs. Test response parity. |

## Current session attack surface summary

**VERIFIED CURRENT BEHAVIOR:** The source contains useful controls: cryptographically random opaque IDs, host-only cookies, HttpOnly/Secure in production, exact CORS origins, trusted Origin checks, revocation and rotation, no JWT in the staff login response, request body size limiting, strict JSON decoding, IP rate limits, separate Super Admin token/cookie, active Admin validation, and tenant claim enforcement.

**OBSERVED DEFECT:** The principal architecture gaps are not “no security”; they are inconsistent/legacy paths, process-local proof/rate-limit state, absent Landing session integration, unproven full route coverage, and undocumented session invalidation policies. This calls for targeted verification and design rather than replacing the established cookie system wholesale.

## Business decisions that gate safe design

1. Is Super Admin required to use MFA and step-up for tenant deletion/refunds/impersonation? Recommendation: yes.
2. Does logout mean this device only, with separate “sign out all devices”? Recommendation: yes.
3. What are idle and absolute session durations, and should “remember me” exist?
4. Is identity globally unique across restaurants, or are tenant-local user records intentional?
5. Do storefront customers need accounts, or should ordering remain anonymous/capability-based?
6. Which exact UI origins are production trusted origins? Do not infer production aliases from staging.

## Validation plan

Use synthetic users and isolated data. Cover session theft/fixation, CSRF from disallowed Origin and missing Origin, CORS preflight, login/refresh replay, old-session replay after logout, cross-tenant IDs/resource access, admin/staff token cross-use, cache poisoning/isolation, rate limits across replicas, account disable/password rotation, Redis outage and 10k-session validation load. Do not test destructive paths against real tenants.
