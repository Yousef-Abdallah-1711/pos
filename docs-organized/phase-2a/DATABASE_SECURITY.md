# Database security model (Phase 2A C010 / C012)

## Identities

| Role | Purpose | Attributes | Privileges |
|---|---|---|---|
| `postgres` (bootstrap) | One-time setup only (create roles, database ownership). **Not used by the API.** | superuser | everything |
| `pos_migrator` | Owns the database and `public` schema; runs `cmd/migrate` | `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS` | DDL on its own schema |
| `pos_app` | The API's runtime connection (`DB_USER`) | `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS` | `CONNECT`, `USAGE` on `public`, `SELECT/INSERT/UPDATE/DELETE` on tables, `USAGE/SELECT` on sequences, `EXECUTE` on functions. No DDL, no `TRUNCATE`, no access to `schema_migrations` |

Created by `backend/scripts/db/create_runtime_roles.sql` (idempotent; takes the database name and both passwords as psql variables). Production Compose runs `backend/scripts/db/init-runtime-roles.sh` only when PostgreSQL initializes a fresh data directory; on existing databases, provision roles and review/reassign ownership before changing credentials. `backend/docker-entrypoint.sh` runs migrations with `MIGRATE_DB_USER/MIGRATE_DB_PASSWORD`, revokes `schema_migrations` from the runtime role, then starts the API with `DB_USER`. Production startup now requires `current_user = pos_app` and rejects superuser or `BYPASSRLS` attributes. Default privileges (`ALTER DEFAULT PRIVILEGES FOR ROLE pos_migrator`) make tables the migrator creates usable by `pos_app` with DML only.

## Verified (disposable stack `docker-compose.pos-test.yml`, `scripts/test-stack/security-smoke.sh`)
- `pos_app` attribute flags all false; `pos_migrator` is not a superuser and cannot create roles.
- The API holds network connections as `pos_app` and none as `postgres`.
- As `pos_app`: reads work; `CREATE TABLE`, `DROP TABLE`, `ALTER TABLE`, `TRUNCATE`, `CREATE ROLE`, `DROP SCHEMA`, `CREATE FUNCTION`, reading/updating `schema_migrations`, and `COPY ... TO PROGRAM` are all denied.
- All 73 smoke checks (auth, tenancy, RBAC, themes, orders, subscription status, ...) pass with the API running as `pos_app`. This is smoke coverage, not exhaustive coverage of every table/endpoint.

## Remaining deployment work
- `docker-compose.prod.yml` now separates bootstrap, migration, and runtime credentials for fresh database initialization. `docker-compose.yml` (development) still connects as `postgres` to preserve the existing local workflow and volume. Existing production databases still need an isolated backup/restore rehearsal of ownership transfer and role switch; do not point the new credentials at an existing volume before provisioning and checking object ownership. Migration 050's explicit `postgres` function grants are supplemented by the runtime role script's default and existing-function grants.
- No TLS requirement on the database connection (`DB_SSLMODE=disable` in all compose files).

Fresh-volume provisioning was verified on disposable PostgreSQL 16 on 2026-11-06: the init script created `pos_app` and `pos_migrator` as non-superuser, non-BYPASSRLS roles and assigned database ownership to `pos_migrator`. Commit: `f8603b272b0c2ce6b29334609ce5fb18c43e1638`.

## Row-level security — staged, NOT enabled on any live table
- Classification of all 91 tables: `DATABASE_TENANCY_MATRIX.md` (45 restaurant-owned, 8 tenant-owned, 12 tenant-owned via FK, 4+7+2 audit-flavoured tenant tables, 3 integration, 3 platform, 5 reference, `tenants`, and the explicitly reviewed global system queue `webhook_retry_queue`, excluded from tenant RLS).
- `internal/pkg/database.WithTenantTx` runs work in a transaction with `app.tenant_id` / `app.restaurant_id` set via `set_config(..., is_local => true)`, so a pooled connection cannot carry a tenant into the next request. Unit-tested with sqlmock (6 tests).
- `internal/pkg/database/rls_pilot_integration_test.go` (`-tags integration`, needs `POS_RLS_ADMIN_URL` and `POS_RLS_APP_URL`) proves the generic pilot policy against the restricted role and a **single-connection pool**. `internal/repository/auth_audit_repository_integration_test.go` applies migrations 040 and 163–166 in an isolated schema, then tests tenant/user ownership, CRUD denial, missing/invalid context, connection reuse, and documented policy rollback against `pos_app`. Migration 166 covers the user-owned `notification_preferences` table; the current application has no repository or route access to this table. The expanded restricted-role test passed against the cloned disposable PostgreSQL 15 database on 2026-11-08. The project migration runner also applied migration 166 as `pos_migrator` to that clone. This verifies only the covered table families and does not close C012.
- **Why not enabled broadly on live tables:** the 363-route API reads and writes through `*sql.DB` directly (repositories take the pool, ~123 endpoints skip use cases, 40 inline SQL closures). With RLS on, any query that does not run inside `WithTenantTx` returns no rows or fails. The auth-audit table is the first migration-backed slice; enabling additional tables requires moving each module's data access to tenant transactions first, family by family, with policies and regression tests added in the same change. Order suggested in `PHASE_2B_HANDOFF.md`.
- Full Go verification after adding migration 165: fresh restricted roles, all repository migrations through 165, `go test -p 1 -count=1 ./...`, `go build ./...`, and `go vet ./...` passed against a disposable PostgreSQL 16 database. The test suite used the disposable database as its administrative test identity; restricted-role RLS enforcement and rollback are separately tested by `TestAuthAuditAndUserSettingsRLSWithRestrictedRuntimeRole`.
- 2026-11-08 migration-166 rehearsal: `cmd/migrate` applied migration 166 as `pos_migrator` to a cloned disposable PostgreSQL 15 database. A second empty disposable database applied migrations 1–166 and 999, then the full Go suite, build, vet, and integration-tagged `internal/pkg/database` and `internal/repository` suites passed. The restricted-role integration test verifies migration 166 inside an isolated schema and rolls its policy back. These checks cover the existing pilot families plus the currently unused `notification_preferences` table only; they do not establish broad transaction-aware repository migration or C012 closure.
- The older `internal/security` RLS manager and `rls_policies.sql` (never applied, schema-incompatible) should be deleted or rewritten, not revived: its tests are quarantined in `backend/tests/EXPERIMENTAL.md`.
- Gate G04/G05 (tenant and restaurant isolation) stays **PARTIAL**: application-level isolation is tested; database-level enforcement is not enabled.
